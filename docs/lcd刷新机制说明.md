# LCD 驱动刷新机制说明

## 两种显示架构对比

### 方式 A：直接写 GRAM（当前驱动采用）

```
MCU 内存                  FSMC 总线               LCD 芯片内部
┌──────────┐             ┌──────────┐            ┌──────────────┐
│ 应用代码  │  set_cursor │  8080-16 │  ↗        │ GRAM         │
│ draw_point│───────────▶│  并行接口 │────▶      │ (240×320×2B) │
│   (...)   │  写GRAM命令 │          │ 写时序     │              │
└──────────┘             └──────────┘            └──────────────┘
```

**流程：**
1. 应用调用 `lcd_draw_point(x, y, RED)`
2. 驱动通过 FSMC 发送 3 个总线周期：设置 X 坐标 → 设置 Y 坐标 → 写入 RGB565 颜色值
3. LCD 芯片内部的控制器自动将颜色写入对应 GRAM 地址
4. LCD 控制器持续从 GRAM 读取数据刷新屏幕（无需 MCU 参与）

### 方式 B：帧缓冲 + 全局刷新（常见大屏/GPU方案）

```
MCU 内存                  FSMC 总线               LCD 芯片内部
┌──────────────────┐    ┌──────────┐            ┌──────────────┐
│ framebuf[240][320]│    │  8080-16 │            │ GRAM         │
│ 　 ≈150KB SRAM   │    │  并行接口 │            │ (240×320×2B) │
│                  │    │          │            │              │
│ draw_point → buf │    │          │            │              │
│   (只改RAM)      │    │   (空闲)  │            │  (显示旧画面) │
│        ↓         │    │          │            │              │
│  lcd_flush() ────┼───▶│  全屏DMA  │───────────▶│  整帧覆盖    │
└──────────────────┘    └──────────┘            └──────────────┘
```

**流程：**
1. 所有绘图操作只修改 MCU 本地 RAM 中的帧缓冲
2. 调用 `lcd_flush()` 时将整个缓冲区（或脏矩形）通过 FSMC 一次性刷入 LCD
3. 刷帧期间 LCD 显示的内容与 MCU 缓冲区可能不一致（撕裂问题）

---

## 为什么本项目采用方式 A

### 1. RAM 限制 — 最根本原因

| 资源 | 大小 |
|------|------|
| STM32F103ZE SRAM | **64 KB** |
| 一帧 RGB565 240×320 | **150 KB** |
| 分块缓冲 240×40 (1/8屏) | **19 KB** |

一帧画面就占 150KB，而芯片总共只有 64KB SRAM。即使使用 1/8 屏分块缓冲（240×40 = 19KB），在当前 6 个任务 + FreeRTOS 堆(15KB) + 全局变量 + 栈的环境下也非常紧张。

**方式 A 的内存开销：0 字节**（直接利用 LCD 芯片自带的 GRAM）。

### 2. 局部刷新性能更好

```
场景：在屏幕上画 5 个字符 "Hello"
方式 A：set_cursor × 5 + write × (5×8)像素 ≈ 45 次 FSMC 操作
方式 B：修改 framebuf 中 45 个像素 + flush 全屏 76800 个像素
```

对于字符显示、菜单更新等典型嵌入式 UI 场景，**90% 的时间只需要修改屏幕不到 5% 的区域**，方式 A 零冗余。

### 3. LCD 芯片自带帧缓冲

ILI9341/ST7789 等驱动 IC 内部有完整的 240×320×18bit GRAM，LCD 控制器自动从中读取数据刷新面板。MCU 只需要像写外部 SRAM 一样写 GRAM 即可，不需要自己维护刷新循环。

```
LCD 芯片内部架构：

  8080 接口 ──▶ 控制寄存器 ──▶ GRAM (240×320)
                                   │
                                   ▼ (60Hz 自动扫描)
                               源极驱动 → LCD 面板
                               栅极驱动 → LCD 面板
```

### 4. 无撕裂问题

方式 B 中如果 flush 和 LCD 扫描不同步，会出现画面撕裂（上半帧是新画面、下半帧是旧画面）。方式 A 每次只改几个像素，人眼几乎感觉不到瞬态不一致。需要无撕裂时，LCD IC 通常支持 TE（Tearing Effect）信号线来同步。

## FSMC 写时序详解

```
8080 并口写周期：
  CS  ──┐         ┌──────────
         └─────────┘
  RS  ─────────────┐          RS=0:写寄存器地址  RS=1:写数据
                    └──────────
  WR  ────┐    ┌───┐    ┌───  每个脉冲写一个16bit字
          └────┘   └────┘
  D[15:0] ──<ADDR>───<DATA>───
```

| 参数 | HAL 配置 | 实际值 @72MHz | LCD 要求 | 余量 |
|------|----------|---------------|----------|------|
| 地址建立 (ADDSET) | 0 → 1 HCLK | 13.9 ns | ≥ 0 ns | ✓ |
| 数据建立 (DATAST) 写 | 1 → 2 HCLK | 27.8 ns | ≥ 12 ns | 2.3x |
| 数据建立 (DATAST) 读 | 15 → 16 HCLK | 222 ns | ≥ 40 ns | 5.5x |

写周期约 42ns，读周期约 236ns（LCD 的 GRAM 读速度是瓶颈）。

## 完整的像素写入流程

```
lcd_draw_point(x=100, y=50, color=RED)
  │
  ├─▶ lcd_set_cursor(100, 50)
  │     │
  │     ├─▶ lcd_wr_regno(lcddev.setxcmd)   // 写寄存器 0x2A (设置列地址)
  │     ├─▶ lcd_wr_data(0x00)              // 列起始高字节
  │     ├─▶ lcd_wr_data(0x64)              // 列起始低字节 (100)
  │     ├─▶ lcd_wr_data(0x00)              // 列结束高字节
  │     ├─▶ lcd_wr_data(0x64)              // 列结束低字节 (100)
  │     ├─▶ lcd_wr_regno(lcddev.setycmd)   // 写寄存器 0x2B (设置页地址)
  │     ├─▶ lcd_wr_data(0x00)              // 页起始高字节
  │     ├─▶ lcd_wr_data(0x32)              // 页起始低字节 (50)
  │     ├─▶ lcd_wr_data(0x00)              // 页结束高字节
  │     └─▶ lcd_wr_data(0x32)              // 页结束低字节 (50)
  │
  ├─▶ lcd_write_ram_prepare()
  │     └─▶ lcd_wr_regno(0x2C)             // 写寄存器 0x2C (写GRAM)
  │
  └─▶ LCD->LCD_RAM = RED                   // RS自动=1 → 数据写入GRAM
        // FSMC 自动产生: CS↓, RS↑, WR↓, D=RED, WR↑, CS↑
```

一个像素需要 **12 个 FSMC 总线周期**（10 个坐标设置 + 1 个命令 + 1 个数据），约 500ns。但对于 240×320=76800 像素的清屏，set_cursor 只调用一次，剩余 76799 个像素各只需 1 个 `LCD->LCD_RAM = color`（因为 LCD IC 会自动递增列地址）。

## 批量写入优化

对于大面积填充，直接写 GRAM 得益于 LCD 芯片的**地址自动递增**：

```c
/* 清屏优化：游标设置一次，剩下的像素逐个写入，地址自动递增 */
lcd_set_cursor(0, 0);       // 1次设置
lcd_write_ram_prepare();     // 1次命令
for (i = 0; i < 76800; i++)
    LCD->LCD_RAM = color;   // 76800次FSMC写，每次LCD内部列地址+1
```

IL9341 支持设置起始和结束地址后的窗口模式，写入超过窗口宽度时自动换行。

## 对比总结

| | 直接写 GRAM（方式 A） | 帧缓冲 + 刷新（方式 B） |
|---|---|---|
| MCU RAM 占用 | 0 | 150KB (全帧) / 19KB (1/8分块) |
| 小面积更新 | 快（只写改动的像素） | 慢（需 flush 整块） |
| 大面积更新 | 快（地址自增+DMA可加速） | 快（DMA 一次性发出） |
| 复杂像素运算 | 慢（无法读写 GRAM） | 快（MCU RAM 随意读写） |
| 适用 STM32F1 | ✓ 原生适合 | ✗ RAM 不够 |
| 适用 STM32F4+H7 | ✓ 也可用 | ✓ 适合（有 SDRAM） |

**总结：** 当前驱动选择直接写 GRAM 不是设计失误，而是 **STM32F103 硬件约束下的最优解**。LCD 芯片自带 GRAM 相当于 "帧缓冲在屏端"，MCU 只需要告诉它"哪些像素改成什么颜色"即可。
